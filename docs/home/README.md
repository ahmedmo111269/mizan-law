## 1. لماذا هذه الحزمة مكتوبة بهذا الشكل

يطلب الأمر التنفيذي لهذه المرحلة **تصميمًا احترافيًا متكاملًا وقابلًا للتنفيذ** لواجهة «مكتب اليوم»، مع التزام صارم بحدود المرحلة التوثيقية: لا شيفرة، ولا قاعدة بيانات، ولا تقنيات، ولا اعتماد قرارات جوهرية من تلقاء الوكيل. الحل المتبع هنا هو نفسه حل حزمة الموكلين:

1. **الفصل بين المواصفة والتنفيذ:** كل ما هو قابل للتنفيذ يُكتب كقاعدة سلوكية أو عقد، لا كخوارزمية ولا كاختيار تقنية.
2. **تثبيت المعتمد قبل الابتكار:** كل جملة جوهرية مسنودة إلى معرف معتمد (`ADQ-xx` / `REQ-xxx` / قاعدة في `docs/DOMAIN_MODEL.md`)، وما لا سند له معلَّم صراحة `[مقترح]`.
3. **فصل «الموصوف» عن «المعتمد»:** بطاقات حالة صريحة في كل جدول.

## 2. قواعد قراءة الحزمة

- `[معتمد]` — سلوك أو حد مقرر في سجل قرارات المشروع؛ يُنفَّذ كما هو.
- `[مقترح]` — تصميم اقترحته هذه الحزمة؛ لا يسري إلا بعد اعتماد صريح.
- `[معلّق]` — مسألة تحتاج قرارًا من صاحب المشروع؛ رقمها في `HOME_OPEN_DECISIONS.md` بصيغة `HD-nn`.
- `[خارج نطاق الصفحة]` — مسؤولية نظام عام أو وحدة أخرى؛ الصفحة تستهلكه ولا تنشئ نسخة موازية.
- `[غير منفذ]` — وظيفة أو مرجع موجودة في الوثائق فقط؛ لا يوجد لها تطبيق قائم اليوم.
- الأسماء الإنجليزية مثل `WorkStream` **مقابض توثيقية** للحديث عن المفهوم، وليست أسماء جداول أو كيانات أو دوال تنفيذية.
- **لا يرد في هذه الحزمة:** شيفرة، أو مخطط SQL، أو جداول، أو مفاتيح، أو أنواع بيانات، أو اختيار إطار عمل أو محرك قاعدة بيانات أو خط خارجي أو خدمة. القرارات التقنية كلها مؤجلة في `docs/TECHNICAL_DECISIONS_PENDING.md`.

## 6. حدود هذه الحزمة بالضبط

- **ما تم:** تصميم وظيفي وتجربة استخدام وهوية بصرية وتجربة شاشات وعقود تكامل وحالات وتخصيص، مع تحقق نظري بالسيناريوهات.
- **ما لم يتم عمدًا:** شيفرة، واجهات منفذة، نماذج أولية تفاعلية، بيانات اختبار، اختيار تقني، خطوط أو مكتبات خارجية، قواعد عمل قانونية أو مواعيد إجرائية محسوبة.
- **ما لا يُفترض:** أن أي `[مقترح]` في هذه الحزمة أصبح قرارًا. لا يُبدأ التنفيذ قبل **بوابتي الاعتماد** المذكورتين في `HOME_DESIGN_REVIEW.md`: اعتماد التصميم أولًا، ثم اعتماد التقنية عند التنفيذ.
