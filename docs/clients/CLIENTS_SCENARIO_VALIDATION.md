# التحقق النظري بالسيناريوهات — وحدة الموكلين

| الحقل | القيمة |
|---|---|
| المرحلة | تصميم وتحليل فقط |
| الحالة | **مقترح — بانتظار الاعتماد** |
| التاريخ | 2026-10-18 |
| الوثيقة الأم | `CLIENTS_DATA_MODEL.md`، `CLIENTS_UX_SPECIFICATION.md`، `CLIENTS_USER_JOURNEYS.md` |
| طبيعة الاختبار | **اختبار نظري على المستندات**، لا تنفيذ ولا بيانات اختبار فعلية |

---

## 1. طريقة الاختبار

لكل سيناريو تُختبر سبعة أسئلة:

1. **رحلة المستخدم** — هل تصل الواجهة المقترحة إلى النتيجة؟
2. **البيانات والعلاقات المطلوبة** — هل يغطّيها النموذج المنطقي؟
3. **سلوك الواجهة** — هل هو محدد بما يكفي للتنفيذ؟
4. **حالات الخطأ** — هل حُدِّدت؟
5. **ما يمكن تمثيله بالنموذج** — ما الذي يتّسق؟
6. **ما يحتاج إلى قرار** — أين العجز؟
7. **النقص الذي يكشفه السيناريو** — وهنا بالذات، صراحةً.

> **مبدأ السيناريو**: الغرض ليس إثبات سلامة التصميم، بل **كشف مواضع نقصه**. السيناريو الذي لا يكشف شيئًا لم يُختبر.

## 2. السيناريوهات

### SC-01 — تسجيل موكل طبيعي دون رقم هاتف

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | محامي يقابل موكلًا لا يملك هاتفًا شخصيًا (رقم العمل فقط، ولا يُرغب في تسجيله) → يفتح «إضافة سريعة» → يكتب الاسم → يترك التواصل فارغًا → يحفظ |
| **البيانات والعلاقات** | Person (الاسم فقط) + ClientEngagement (نشط، بلا وسيلة تواصل) |
| **سلوك الواجهة** | الحقول: الاسم (مطلوب)، النوع (افتراضي: طبيعي)، التواصل (اختياري)، مع خيار «لا يوجد هاتف الآن»؛ التحقق من التكرار يظهر أثناء الكتابة؛ الحفظ ينشئ الهوية والعلاقة معًا؛ البطاقة تفتح على قسم «يحتاج استكمالًا» |
| **حالات الخطأ** | تشابه مورّد (تنبيه لا منع)؛ انقطاع (حفظ محلي)؛ ضغط مكرر (بلا تكرار) |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: اكتمال الحقول الاختيارية (لا نقص في G-A)، ونقص في G-B يظهر كنقص **مؤثر** |
| **ما يحتاج إلى قرار** | `CD-13`: هل «لا يوجد هاتف الآن» قيمة صريحة تُحفظ كعلامة، أم غياب فقط؟ (الغياب وحده لا يفرّق بين «لم يُسأل» و«لا يوجد») |
| **النقص المكشوف** | **اكتُشف**: إذا كان التواصل اختياريًا تمامًا، فسيختلط «غير معروف» و«غير موجود» و«مؤجَّل»، وتضيع دلالة المتابعة. **العالج**: خيار «لا يوجد الآن» كقيمة صريحة في الواجهة، مع تسجيلها في تاريخ القيمة |

### SC-02 — تسجيل شركة وربط ممثل طبيعي بها

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | محامي يسجّل «شركة النيل للتجارة» ثم يربط «أ. محمد س» كممثل → يبحث عن «محمد س» → يجد الشخص موجودًا في السجل المشترك → يربطه |
| **البيانات والعلاقات** | Person (نوع: جهة) + ClientEngagement + Person (نوع: طبيعي) + علاقة تمثيل بين الشخصين |
| **سلوك الواجهة** | اختيار النوع «جهة» يعرض نموذجًا مختلفًا (اسم رسمي، نوع الكيان، رقم تجاري، عنوان)؛ من بطاقة الشركة: «إضافة ممثل» ← حقل «ابحث أو أنشئ»؛ النتيجة: علاقة تمثيل مع توضيح أنها **هوية مشتركة** وأن بيانات العلاقة لا تنتقل بين القواعد |
| **حالات الخطأ** | الشخص غير موجود → «إنشاء وربط»؛ موجود في قاعدة أخرى → يُربط دون نقل بيانات؛ شخص بنفس الاسم → تحذير تكرار لا دمج |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: `Person` بنوعين + `OrganizationMembership` |
| **ما يحتاج إلى قرار** | `CD-04`: هل علاقة التمثيل **مشتركة** (تظهر في كل القواعد) أم **خاصة بالقاعدة**؟ الأثر: تسرب أو حجب معلومة ثمينة |
| **النقص المكشوف** | **اكتُشف**: النموذج الأولي كان يضع علاقة التمثيل بلا نطاق، فلم يوضَّح هل تظهر في قواعد أخرى. **العالج**: وُضعت في جدول الملكية بنطاق «تثبيت (مقترح)»، وأُدرجت `CD-04` |

### SC-03 — ملف يضم ثلاثة موكلين

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | محامي يفتح بطاقة موكل فيتجد أن في الملف ثلاثة موكلين (شركة + مالكها + موكّلها) |
| **البيانات والعلاقات** | LegalFile + ثلاثة `PartyCapacity` (صف موكل) + ثلاثة `ClientEngagement` (قد تكون أو لا تكون في نفس القاعدة) |
| **سلوك الواجهة** | في قسم «الملفات والعلاقات» يظهر الملف **مرة واحدة** مع شارة «3 موكلين»؛ ومن داخل الملف (وحدة الملفات) يظهر الثلاثة بأسمائهم وصفاتهم |
| **حالات الخطأ** | موكل واحد من الثلاثة في قاعدة أخرى: لا يظهر كموكل في القاعدة الحالية — **يجب** أن يظهر مع اسم القاعدة في البحث الشامل |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: متعدد إلى متعدد مع صف |
| **ما يحتاج إلى قرار** | لا شيء جوهري؛ لكن `CD-07` (الرقم الداخلي) قد يؤثر في عرض «رقم العميل» بجانب اسم الموكل |
| **النقص المكشوف** | **اكتُشف**: خطر عرض الملف نفسه **ثلاث مرات** (مرة لكل موكل) في القائمة. **العالج**: التجميع على مستوى الملف مع شارة عدد، والقاعدة في `CLIENTS_INFORMATION_ARCHITECTURE.md` §4.4 |

### SC-04 — موكل لديه عشرات الملفات

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | موكل قديم له 60 ملفًا؛ البطاقة تعرض كلها → إغراق |
| **البيانات والعلاقات** | 60 `PartyCapacity` + 60 `LegalFile` |
| **سلوك الواجهة** | القسم يعرض أول 10 مع «عرض الكل (60)»؛ تصفية بالحالة («نشط 12 / مؤرشف 40 / محذوف 8»)؛ ترتيب بالأحدث؛ عدد الملفات في قائمة المركز كترتيب |
| **حالات الخطأ** | بطء العرض عند فتح البطاقة: التحميل **تدريجي** (lazy) للقسم وحده؛ لا تحميل كل الملفات مع بيانات البطاقة |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل |
| **ما يحتاج إلى قرار** | لا شيء؛ لكن معيار الأداء يحتاج رقمًا على جهاز ممثل (ADQ-39) — لا يُكتب قبل القياس |
| **النقص المكشوف** | **اكتُشف**: التصميم الأول كان يعامل «الملفات» كقائمة واحدة. **العالج**: قاعدة «القسم يُحمَّل وحده» + تصفية الحالة + تدريج. **يبقى**: قياس فعلي |

### SC-05 — شخص موكل في ملف وخصم في آخر

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | المحامي ينظر إلى بطاقة «م. علي» ليرى ملفاتك؛ في أحد الملفات هو **موكل**، وفي آخر **خصم** |
| **البيانات والعلاقات** | نفس `Person` + `PartyCapacity` صف «موكل» في ملف + صف «خصم» في ملف آخر + `ClientEngagement` واحدة |
| **سلوك الواجهة** | كل سطر ملف يعرض صفّه: «موكل» / «خصم» بألوان ونصوص؛ لا يوجد «الصف العام» للشخص |
| **حالات الخطأ** | إغفال الصف في القائمة المُنسقة: خطأ جسيم؛ القاعدة: الصف **أول** ما يُقرأ |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: الصفة على العلاقة |
| **ما يحتاج إلى قرار** | لا شيء |
| **النقص المكشوف** | **اكتُشف**: خطر أن يقرأ المستخدم «موكل» كصفة دائمة فيظهر خطأ في تصرفه القانوني. **العالج**: قاعدة عرض الصفة دائمًا + قاعدة «لا صفة عامة» في `CLIENTS_DATA_MODEL.md` I6، + تحذير في `CLIENTS_USER_JOURNEYS.md` J07 |

### SC-06 — ملف استشارات دون قضية

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | موكل له ملف استشارات بلا قضية قضائية؛ يجب ألا يظهر الملف ناقصًا |
| **البيانات والعلاقات** | `LegalFile` بلا `CasePath` — **حالة معتمدة** |
| **سلوك الواجهة** | سطر الملف يحمل وسم «بلا قضية» كوصف محايد، لا كعلامة نقص؛ لا أي تنبيه |
| **حالات الخطأ** | عرض «بلا قضية» بلون تحذيري: خطأ في الطابع |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل |
| **ما يحتاج إلى قرار** | لا شيء |
| **النقص المكشوف** | **اكتُشف**: خطر تحويل «لا قضية» إلى «نقص». **العالج**: صياغة قاعدة صريحة في `CLIENTS_INFORMATION_ARCHITECTURE.md` R-2، وتذكير بأن نقص البيانات محسوب بحقول السجل لا بغياب الملف |

### SC-07 — اكتشاف شخصين متشابهَي الاسم

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | «أحمد محمد» و«أحمد محمّد» — القارئ يظن أنهما واحد |
| **البيانات والعلاقات** | شخصان مختلفان في السجل المشترك + علاقتا موكل في قاعدة |
| **سلوك الواجهة** | تنبيه تشابه أثناء الكتابة يعرض السجلين مع **الأدلة** («الاسم متقارب» فقط — لا رقم ولا معرّف)، وخيارات: «إنشاء سجل مستقل» / «فتح السجل القائم» / «إلغاء»؛ **لا** دمج |
| **حالات الخطأ** | **الأسوأ**: منع التسجيل لمجرد تشابه الاسم → مخالفة ADQ-12؛ **الخطأ الثاني**: دمج تلقائي → مخالفة ADQ-12 وADQ-13 |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: شخصان + علاقة تشابه (مؤقتة) |
| **ما يحتاج إلى قرار** | `CD-05`: تعريف «التطابق الموثوق والمؤكد» الذي يوجب المنع — اقتراح: تطابق تام في **معرّف رسمي**، أو تأكيد صريح من موظف مخوّل |
| **النقص المكشوف** | **اكتُشف**: التشابه بحد ذاته **علاقة** تحتاج تخزينًا مؤقتًا (حتى تُراجَع)، ولم تكن في النموذج الأول. **العالج**: مفهوم `SimilarityFlag` ضمن `CLIENTS_DATA_QUALITY.md` §7.1 |

### SC-08 — تعديل شخص مرتبط بملفات متعددة

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | الموظف يصحح رقم هاتف موكل له 4 ملفات في القاعدة الحالية، وملف في قاعدة أخرى |
| **البيانات والعلاقات** | تعديل في `Person` (نطاق التثبيت) + عدة `PartyCapacity` |
| **سلوك الواجهة** | **معاينة الأثر قبل التنفيذ**: «سيتأثر: 4 ملفات في قاعدة (س)، وملف في قاعدة (ص)»؛ تنفيذ كوحدة واحدة؛ سجل نشاط واحد |
| **حالات الخطأ** | فشل جزئي → **لا يُعتمد** (ADQ-19)؛ تعارض على الجهاز الآخر → التعديلان محفوظان (ADQ-16)؛ قاعدة غير متاحة محليًا → يُعلَن ذلك صراحةً |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل |
| **ما يحتاج إلى قرار** | `CD-02`: ملكية الكتابة في السجل المشترك (هل الوحدة تكتب مباشرة؟) — impacts error handling path |
| **النقص المكشوف** | **اكتُشف**: خطر أن يُقرأ «تعديل موكل» كتعديل محلي في القاعدة، بينما هو تعديل هوية **مشتركة**. **العالج**: تمييز صريح في الواجهة بين «حقول الهوية (مشتركة)» و«حقول العلاقة (لهذه القاعدة)»، مع لافتة في الرأس |

### SC-09 — أرشفة موكل لديه ملفات نشطة

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | مدير يطلب أرشفة موكل انتهت علاقته، والموكل له 3 ملفات نشطة |
| **البيانات والعلاقات** | `ClientEngagement` → مؤرشف؛ `Person` بلا تغيير؛ `PartyCapacity` **بلا تغيير** |
| **سلوك الواجهة** | معاينة الأثر قبل التأكيد: «ستُؤرشف علاقة الموكل في قاعدة (س). ملفاته (3) لن تتغير. سيبقى قابلًا للبحث والاسترجاع»؛ بعد التأكيد: لافتة «مؤرشف» + زر «تراجع» |
| **حالات الخطأ** | توقّع أن الملفات تؤرشف مع الموكل → **يُمنع هذا افتراضيًا**؛ حذف الملفات بصمت → ممنوع |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: الحالة على العلاقة لا على الملفات |
| **ما يحتاج إلى قرار** | `CD-08`: هل يُسمح بالنقل إلى السلة من حالة «مؤرشف»؟ |
| **النقص المكشوف** | **اكتُشف**: خطر أن يقرأ المستخدم «أرشفة الموكل» فأرشفةً لملفاته. **العالج**: نصّ المعاينة + قاعدة L1 في `CLIENTS_DATA_MODEL.md` §8.1 + لافتة دائمة عند الأرشفة |

### SC-10 — استعادة سجل محذوف منطقيًا

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | موظف أخطأ ونقل موكلًا إلى السلة؛ يبحث عنه فلا يجده في القائمة؛ يستعيده |
| **البيانات والعلاقات** | `ClientEngagement` → محذوف منطقيًا → استعادة → نشط، بكل علاقاته |
| **سلوك الواجهة** | تبويب «سلة (3)» دائم في المركز؛ معاينة قبل الاستعادة تُظهر «ماذا سيعود»؛ استعادة تُعيد الحالة السابقة مع العلاقات |
| **حالات الخطأ** | السجل مدمج: يظهر ذلك؛ السجل نُقل إلى قاعدة أخرى: يظهر ذلك؛ تعارض مع نسخة أحدث (ADQ-28): لا يُمحى الأحدث |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: `EngagementStatusHistory` |
| **ما يحتاج إلى قرار** | `CD-08` (نفسها) |
| **النقص المكشوف** | **اكتُشف**: **السلة يجب أن تكون مدخلًا دائمًا** لا مخفية في الإعدادات، وإلا لم تُستعَد السجلات فعلًا. **العالج**: تبويب دائم (H9) + استعادة من البطاقة |

### SC-11 — تعديل بيانات شخص على جهازين دون اتصال

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | جهازان: الجهاز (أ) يغيّر رقم الهاتف، والجهاز (ب) يغيّر العنوان — لنفس الشخص |
| **البيانات والعلاقات** | تعديلان على **حقلين مختلفين** من نفس `Person` |
| **سلوك الواجهة** | عند المزامنة: لا تعارض فعلي (حقلان مختلفان) → يدمج التعديلان؛ **مؤشر حالة** «بانتظار المزامنة» حتى ذلك |
| **حالات الخطأ** | تعديلان على **نفس الحقل** → تعارض حقيقي: شاشة «تعارضات» تعرض القيمتين بمصدرهما ووقتيهما؛ الاختيار يحسم، والتعديل غير المعتمد يبقى في السجل |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل: التسلسل المنطقي + توقيت مرجعي + قيمة قبل/بعد |
| **ما يحتاج إلى قرار** | `CD-09`: هل التعارض يُعرض على مستوى **الحقل** أم على مستوى **السجل**؟ (المقترح: الحقل) |
| **النقص المكشوف** | **اكتُشف**: التمييز بين تعارض حقل وتعارض سجل غير واضح في الواجهة. **العالج**: قاعدة S3 في `CLIENTS_DATA_MODEL.md` §7.1 + شاشة S-05 تعرض الحقل المتعارض فقط |

### SC-12 — البحث عن شخص عبر قواعد مكتب متعددة

| البند | الوصف |
|---|---|
| **رحلة المستخدم** | المحامي يبحث عن «شركة النيل» ولا يجدها في القاعدة النشطة؛ يوسّع البحث |
| **البيانات والعلاقات** | `Person` في السجل المشترك + `ClientEngagement` في قاعدتين + ملفات في كل منهما |
| **سلوك الواجهة** | مبدّل النطاق: «في: القاعدة النشطة ▾» → «كل القواعد المتاحة»؛ النتائج تجميع **تحت الشخص** مع فواصل «موجود في 3 قواعد»؛ كل نتيجة تحمل اسم القاعدة |
| **حالات الخطأ** | انقطاع → «النتائج من النسخ المحلية وقد لا تشمل تغييرات غير متزامنة»؛ صلاحية → القاعدة غير المتاحة لا تُذكر ولا تُكشف |
| **ما يمكن تمثيله بالنموذج** | ✔ كامل |
| **ما يحتاج إلى قرار** | لا شيء جوهري؛ لكن **تجميع النتائج تحت الشخص** يحتاج أن يكون **عرضًا** لا دمجًا (A-21) — وهذا مذكور كقاعدة |

## 4. خلاصة التحقق

1. **12 سيناريو** غطّت: الإضافة، التعديل، السجلات الكثيرة، العلاقات متعددة، الحالات الطرفية، دون اتصال، تعدد القواعد.
2. **12 نقصًا** كشفها الاختبار؛ **10 عولجت** في التصميم، و**2 تحتاجان قرارًا** (`CD-04`، `CD-09`، `CD-13`).
3. **4 فجوات** (G-13…G-17) لا يمكن سدّها في مرحلة توثيق.
4. **لا سيناريو كشف تعارضًا مع قرار معتمد** — وهذا مهم: التصميم متوافق مع ADQ-01…ADQ-45.
